Build an internal vibe coding app with the Cursor SDK

Your team describes an app in plain language, a Cursor agent builds it in a governed repo, and your pipeline ships it to Azure.

Read the summary See the steps

JSPrepared for ConocoPhillips by Jordan Stein, Field Engineer, Cursor

The whole approach, in one read

Everything below the diagram is detail. If you only read this part, you have the plan.

  1. People describe the app they need in a prompt box, and a server route calls Agent.create() to turn each request into a Cursor cloud agent, using a service account key that never leaves the server.
  2. Every agent starts from a template repo whose rules, hooks and environment pin your approved stack and block risky commands such as deploys.
  3. Progress streams back to the requester as it happens, and each request lands on its own branch with its own pull request in GitHub.
  4. Nothing ships without a person signing off. GitHub Actions runs your tests, deploys a preview app on Azure, and change requests go back to the same agent.
  5. Merging is the deploy. GitHub Actions signs in to Azure with short-lived OIDC credentials and ships the merged commit to Azure App Service, so agents never hold Azure credentials.
  6. Tag every agent, track spend per generated app, and fold repeat review feedback back into the template.

01

Line up the prerequisites

A paid Cursor team, GitHub connected to Cursor, an Azure subscription, Node.js 22.13 or later, and a server-only API key.

You need a Cursor team on a paid plan, a GitHub organization that holds the template repo and runs GitHub Actions, an Azure subscription with the Azure CLI installed, and Node.js 22.13 or later. Connect GitHub under Integrations in the Cursor dashboard and give the Cursor GitHub app access to the template repo, so cloud agents can clone it, push branches and open pull requests. For a shared internal app, use a service account API key so usage bills to the team, and keep it strictly on the server.

With a service account key, pull requests open as the Cursor GitHub App. The SDK's openAsCursorGithubApp option defaults to true for service account keys, so agent pull requests come from the app rather than a person, and the app needs write access to the template repo. See the GitHub integration docs.

02

Install the Cursor SDK

Install @cursor/sdk, then ask Cursor.models.list() which models your team allows.

The package is scoped, so install @cursor/sdk. Before you pick a model, ask the SDK which ones your team allows rather than hard-coding a guess.

Confirm models with Cursor.models.list(). Model ids and features vary by plan and team settings, so treat the list as the source of truth before you hard-code one.

03

Give agents a template repo with guardrails

Rules, hooks and environment config pin your approved stack and block risky commands.

Every generated app starts from a starter repo in GitHub that pins your approved stack. Project rules in .cursor/rules shape what the agent writes, .cursor/hooks.json can block risky shell commands such as deploys, and .cursor/environment.json lets cloud agents install dependencies and run your tests. Include a Dockerfile, since that is the container image Azure App Service runs, and the .github/workflows/deploy.yml from step 07.

See the Rules and Hooks docs for the file formats. Hooks are file-based only, so the guardrails live in the template rather than in your server code.

Back the rules with a CODEOWNERS entry for .github/. A rule asks the agent not to touch the pipeline; code owners plus branch protection make sure any change to it still needs platform-team review.

04

Wire the prompt box to a server route

The route checks who is asking, creates a cloud agent on the template and sends the prompt.

The browser posts the plain-language request to your route. The route confirms who is asking, creates a cloud agent on the template repo, tags it with the requester, and sends the prompt. Each request ends up on its own branch with its own pull request.

Run one agent against your template first to confirm autoCreatePR opens the pull request in GitHub before you build on it.

If GitHub isn't connected for your team, Agent.create() throws IntegrationNotConnectedError with a provider naming the missing integration and a helpUrl to reconnect. Log it for whoever runs the builder app.

requireUser is a placeholder for your own SSO or auth check. Reject the request before any agent is created.

05

Stream progress back to the requester

Relay run.stream() as server-sent events, then send the final status and pull request link.

Relay run.stream() events as server-sent events so people can watch the agent plan, edit and test. When it finishes, run.wait() returns the final status and the pull request link.

prUrl is only set when a pull request opens. Handle it being undefined, for example when the run fails or makes no changes.

Cloud runs keep going if the browser disconnects, so you can reattach later with Agent.getRun() or Agent.resume().

06

Review, preview and iterate

A person approves every change, and follow-ups go back to the same agent.

Nothing ships without a person signing off. Reviewers open the pull request in GitHub, a required status check runs GitHub Actions for your tests, and a preview app on an Azure App Service deployment slot gives them a URL to try it, posted as a comment on the pull request (step 07). Require an approving review in the same branch protection rule so a person approves before anything merges. Change requests go back to the same agent, so it keeps the full conversation and context.

For a fast local loop while you build, the Cursor Cookbook app-builder runs a local agent against a hot-reloading preview.

07

Deploy to Azure

Merging is the deploy, through GitHub Actions to Azure App Service.

Merging is the deploy. Agents never hold Azure credentials; GitHub Actions signs in to Microsoft Entra ID with a federated OIDC credential for each run, and rolling back is just a revert through the same path. Every generated app runs as a Linux container on Azure App Service, built from the Dockerfile in the template and pulled from Azure Container Registry, and the builder app itself can run there too. Each app gets a URL on <app>.azurewebsites.net, and each deployment slot gets its own on <app>-<slot>.azurewebsites.net.

Prepare the subscription once. Create a resource group, a container registry, a Linux App Service plan that supports slots, the app with a staging slot, and let the app pull from the registry with its managed identity.

Then create the identity GitHub Actions signs in as. Its federated credential only accepts OIDC tokens from your template repo's production environment (add a second one for preview), so no other repo, and no long-lived secret, can deploy.

One workflow in the template does three jobs. On a pull request it runs the tests, deploys a preview to a deployment slot named after the pull request, and comments the preview URL on the pull request. After merge it deploys the merged commit to the staging slot and swaps it into production, so the new version is warm before it takes traffic. When a pull request closes, merged or not, it deletes that preview slot. The official azure/login and azure/webapps-deploy actions do the sign-in and the deploy.

GitHub runs pull request workflows straight from the YAML, so there is no pipeline to register. Protect main once so the deploy check and an approving review are required before anything merges.

Run the builder app on App Service the same way, and keep the Cursor API key in Azure Key Vault. A Key Vault reference in the app settings resolves the secret at runtime through the app's managed identity, so the key never appears in the image, the app configuration or the repo.

<subscription-id>, <client-id>, your-org and the resource names are placeholders. github-deploy-role.json is a least-privilege custom role scoped to the resource group: push to the registry, and create, deploy, swap and delete App Service slots, which preview cleanup needs. The template's azure/ folder has a starting point. See Use GitHub Actions with OpenID Connect.

App Service apps are reachable from the internet by default. For internal-only apps, add access restrictions or a private endpoint and VNet integration on the plan, and agree the exposure with your platform team.

If production needs a change approval, add required reviewers to the production GitHub environment. The production deploy then waits for that sign-off without any change to the workflow.

Why App Service and not Static Web Apps? The template is a small Node server with a /ping health check, shipped as a container, which App Service runs as is. Static Web Apps suits static front ends; if your generated apps are pure HTML, it is a lighter option with built-in pull request preview environments. Premium v3 plans allow up to 20 slots per app, which caps concurrent previews.

08

Govern it and keep improving

Tag agents, track spend per app, archive what you no longer need, and refine the template.

Tag every agent, track spend per generated app, and archive what you no longer need. SDK runs follow your team's Privacy Mode and model settings, and their spend appears under the SDK tag in the usage dashboard. When reviewers keep asking for the same fix, fold it into the template's rules.

cost can take a moment to settle after a run ends and is absent until it does, which is why the example reads it with optional chaining.
